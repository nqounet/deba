# ADR: 永続セッション・ワーカー（Stateful Bulk Agent）構想の非推奨化と Stateless Multi-Agent アーキテクチャへの移行

## コンテキスト
`004_eternal_session_worker.md` および `005_interactive_bulk_agent_project.md` において、「1リクエスト＝1カウント」というAPIの制限を回避するため、長期間のセッションを維持し、大量のタスクを一括処理（Stateful & Interactive Bulk）するアーキテクチャが提案されていました。

## 課題（技術者視点でのレビュー結果）
1. **APIの仕様との不一致によるコスト悪化**
   一般的なLLM API（Gemini APIやOpenAI API）における「セッション」とは、クライアント側で会話履歴を保持して毎回全体を再送信するラッパーに過ぎません。トークンベースの従量課金環境下においてこのアプローチを採用すると、リクエスト毎の送信トークン数が雪だるま式に増加し、コスト効率が向上するどころか劇的に悪化（トークン爆発）します。
2. **Lost in the Middle / ハルシネーションの増加**
   大量のタスクとファイル内容を1つのコンテキストに押し込むことで、LLMが過去の文脈と現在のタスクを混同するリスクが高まります。
3. **PlanとExecuteの分離欠如**
   「戦略を立てる軍師」と「手を動かす足軽」を同一プロンプト内で演じさせることは、LLMの推論能力（IQ）を不要に圧迫します。

## 決定事項
* **Stateful Long-Session の廃止**: `004` および `005` で提案された「永続セッション」の設計思想を非推奨とします。
* **Stateless Multi-Agent の推進**:
   * 現在の実装（`deba plan` で計画を作り、`deba run` または `deba worker` で各ステップを個別に実行するアーキテクチャ）を正とします。
   * タスクごと、またはステップごとにコンテキストをリセットし、必要な情報（対象ファイルの内容等）だけを都度注入する Stateless なアプローチを徹底します。
* **フェイルセーフの強化**: 無限ループを防ぐための明確なブレーカー（例: MAX_RETRIES）と、コンテキストの刈り込み（エラーログのトランケート）を実装・維持します。

## 影響
* API利用料の最適化（不要な過去のコンテキストの再送信を防ぐ）。
* 実行の安定性向上（タスク間のコンテキスト汚染による破壊的変更の防止）。
* プロンプト設計の単純化（役割分担による特化）。
